Invoice preview — five directions

What the view action opens: the vendor’s own document, and every field the parser pulled out of it. Same content in all five; they differ in where the document sits relative to its data.

Two things every version has to handle. Not every invoice has a document — when a receipt only ever existed as an email body there is no PDF, just source.html, and the preview must show the fields with an explanation instead of an empty frame. And the fields shown are the real ones from invoice.json; the page image is a drawn placeholder, because the actual PDF is a live financial record and does not belong referenced from docs/.

A

Modal

centred, document above its data open ↗

The document and the fields read as one column, top to bottom.

  • Works at any width — the same layout on a laptop and a phone
  • You scroll to get from the document to the fields
  • Familiar; nothing to learn
  • Wastes the sides of a wide screen
B

Split

document beside its data open ↗

Document left, extracted fields right, each scrolling independently.

  • Both visible at once — you can check a number against the page without scrolling, which is the whole point of a preview
  • Best use of a wide screen
  • Needs ~1040px; collapses to stacked below 860px
C

Drawer

slides in, list stays visible open ↗

A panel from the right. The invoice list stays on screen behind it.

  • Keeps context — you can see which row you opened
  • Natural home for next/previous stepping through invoices
  • Narrow, so the page renders small and the fields wrap
  • Least room for the document, which is the main thing you came to see
D

Inline

the row expands in place open ↗

No overlay at all. Clicking a row opens the detail inside the table, between the row and the one below it.

  • Most context of any version — the row stays put and its neighbours stay readable
  • Nothing to dismiss; clicking the row again closes it
  • Document height must be capped, or one invoice pushes the rest of the list off screen
  • Two open rows at once would get unwieldy — likely single-open
  • No modal, no scrim, no focus trap: the least new machinery to build
E

Inline, refined

D, given a hierarchy. The direction that was taken open ↗

Version D’s layout, with the fields given a hierarchy instead of three equal key/value lists. Rebuilt on the design system the share flow landed; the same screen sits in that flow as step 1b, whose build.py is canonical for this markup.

  • The money leads - the amount is what you opened the row to check, so it is the panel’s headline with net and VAT beside it, and it is not repeated in the list below
  • Every other field is a label/value row on the same hairline rhythm the share page uses, and identifiers are monospaced so they can be read character by character
  • The document is a thumbnail, not a viewer - no width this panel can afford makes an A4 page readable, so the box is sized to be recognised and reading it is what opening it full size is for
  • The open row drops the accent. A ticked row carries it; disclosure was borrowing the same tint, so two unrelated states were one colour. The row and its panel take the page colour instead, cut into the card as a well
  • Still more CSS to maintain than D, and the hierarchy is still an opinion about what matters
