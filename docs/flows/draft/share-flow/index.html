Share flow

Handing a batch of invoices to someone who has no account — an accountant, a co-founder, a client. Each frame is a real page using the app’s own tokens.css and dashboard.css, so these cannot drift from the product. Everything here is to build; the dashboard chrome around it already exists.

Two clicks to a live link. Update, then the share icon — the link is minted and on the clipboard before any dialog asks anything. Five things deliberately do not exist, because each one is a decision the user would otherwise make before getting their link:
  1. No share dialog. The click is the share. The popover reports, it does not ask.
  2. No expiry, password, or permission levels. Live until revoked; revoke is the one switch.
  3. No separate preview. “Open link” opens the exact URL the recipient gets.
  4. No picking. The link is the batch — no checkboxes, no partial zip. Wrong batch? Tick rows on the dashboard and share again; it is still two clicks.
  5. No attachments. The mail carries the summary and a button. 12 MB does not.

Data model, routes, thumbnail generation and the mail transport: design.md. Who sees what: Owner needs the owner_key its browser kept; Anyone with the link does not.

The share page

GET /s/{token} Anyone with the link open full screen ↗

Summary first: filename, count, size and date range — one line that catches a wrong export before anyone opens anything.

Below it the page is laid out as the zip’s contents: a pdf part on a grey band and a csv part on white, each named and chipped with its file type, under a header already chipped zip. No sentence says “you are downloading PDFs and a spreadsheet” — the layout says it. The five thumbnails are rendered server-side at extraction time; page one of an invoice is recognisable at 240px, which is the highest signal-per-pixel the page can offer for free. Five is the whole strip — it never scrolls, so there is no lazy loading and nothing to virtualize.

The table is a sheet, not a working surface — and that is the point of contrast with the dashboard, which has checkboxes, vendor logos, per-row actions and 52px rows. Here: hairline grid, 30px rows, tabular figures, the zip’s own filenames, and counts on the last line. Eight columns, all of them real output from extract.py: #, Vendor, Invoice #, Document, Issued, Net, VAT, Total. The net/VAT split is on screen because it is the reason the batch was sent. Row 6 shows dashes where Bolt’s ride receipt carries no invoice number and no split — that is the real shape of the data, not a placeholder.

The ninth column is not data: it counts what the CSV has and the page does not (+15 in csv, with a … per row). Without it the sheet reads as the whole truth and invoices.csv looks like a copy of it. Narrow screens drop columns into that count — +15, +18, +19 — so the number stays true at every width. Nothing on this page is clickable except Download — no row opens, no thumbnail opens, there is no viewer to build and no single-document route to serve. Whoever wants to read one downloads the zip and opens it in the reader they already have. The pink strip is the only owner-only thing on the page, and it is the whole difference between this and screen 8.

Optional — sending it for them

4

Composer

Owner open full screen ↗

One field the user must fill: the address. Subject and body are already drafted, and the mail goes out from a connected mailbox — Unipile already holds those credentials, so there is no second OAuth and no Gmail client to write.

From states the answer rather than asking a question — the address as text, the way it would read on a sent message, with a caret beside it if there is anywhere else to send from.

The draft is right there underneath, in an iframe over the real rendered mail — the same document the API sends, not a mock-up of it, so what the sender approves and what the recipient opens cannot diverge. It also answers the question a bare To-field leaves hanging: what is this going to say in my name?

5

Choosing the mailbox

GET /accounts Owner open full screen ↗

The caret exists only because two mailboxes are connected; with one it is not rendered, because a control that leads nowhere is worse than no control. With two — personal and billing, say — which one sends is a real question, and it decides where the reply lands. The current mailbox stays in the list and is ticked, so the menu answers which am I on? as well as what else is there? The choice is remembered, so it is asked once rather than every time.

The email

Recipient open full screen ↗

Shaped like a receipt: a branded band, one heading, the figure that matters, a short label/value block, one action, then quiet link rows. No thumbnails, no vendor list, no marketing — the page has all of that, and an inbox is not where anyone reviews 37 invoices. Dropping the images also drops the third of clients that block them.

600px, tables, inlined styles, plain-text alternative — the format that survives Outlook. No attachment: 12 MB bounces, lands in spam and goes stale; a link does none of that.
