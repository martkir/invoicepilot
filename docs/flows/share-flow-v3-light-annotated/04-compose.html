  4. 4The preview

    GET /api/s/{token}/email/preview

    shares · newinvoices

    -- the manifest queries again, for the summary the mail quotes
SELECT token, invoice_ids, owner_name, expires_at
FROM shares WHERE token = $1;

SELECT id, issued_on, data FROM invoices
WHERE id = ANY($1::text[])
ORDER BY issued_on DESC NULLS LAST, id;

    Serves the rendered mail as a document, for the composer's iframe to load. It exists so the preview is the bytes the send will use rather than a second template that can drift from it: one renderer, called here with the response written to the iframe and called on the send with the same output handed to Unipile. The mail names the owner twice and its footer names the expiry date, so both come out of this row rather than out of the template.

    The iframe's `src` is the route: the composer fetches the rendered mail rather than drawing one. Loading is what makes it the real thing - the same renderer, the same row, the same bytes the send will hand to Unipile.

    Answered. No route in any spec served this, and the design rules out the alternative by name: the iframe must show what is about to be sent, not a look-alike. Settled 2026-08-15 - the route exists, GET /api/s/{token}/email/preview, and it is the tenth endpoint in the map. A second template that could drift from the sending one was the only other answer.

    The one route the owner key gates. `from_account_id` arrives from the browser, so it is checked against /api/accounts on the way through - the only thing that may send as a mailbox is that mailbox's owner. services/api/src/invoicepilot/unipile.py has no send function yet; this is the one call it is missing.

    Carries the address, the chosen account and the owner key. The share is already live - mail is the optional half of the flow.
