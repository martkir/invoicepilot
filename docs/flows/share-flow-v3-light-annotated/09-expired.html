A 410, and the reason the manifest query is written the way it is.

  1. 1This link has expired

    GET /api/s/{token}

    shares · newinvoices

    SELECT token, invoice_ids, owner_name, owner_email,
       created_at, expires_at
FROM shares WHERE token = $1;     -- primary key, no index needed

SELECT id, issued_on, data FROM invoices
WHERE id = ANY($1::text[])
ORDER BY issued_on DESC NULLS LAST, id;

    Two queries, and the first one deliberately does not filter on expires_at. `WHERE expires_at > now()` would fold an expired share into a missing one and cost the page the difference between 410 and 404 - which is the difference between the two dead-end screens. The row is fetched, then the expiry is compared. It also carries `owner_name` and `owner_email`, which is what lets the recipient's page name a person: they have no account and can be shown nothing this response does not hold.

    The row came back and `expires_at` had passed: 410 Gone. This is why the first query does not say `WHERE expires_at > now()` - a filtered query returns no row for an expired share and could only ever answer 404, which is the other screen and the other instruction to the reader. The 410 body carries the two owner fields and the two dates and nothing else: no invoice ids, no manifest, because the second query is never run once the expiry has failed.

    Answered. Drawn as a revoked share until 2026-08-15, when the screens caught up with the TTL: nobody turns a link off, its seven days run out. Same page, same status code, different cause - and no DELETE route to serve it.
