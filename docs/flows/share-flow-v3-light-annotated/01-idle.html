  3. 3Update

    POST /api/scan -> GET /api/scan/{job_id}

    invoices

    INSERT INTO invoices (id, issued_on, data)
VALUES ($1, $2, $3::jsonb)
ON CONFLICT (id) DO UPDATE
   SET issued_on = EXCLUDED.issued_on, data = EXCLUDED.data
RETURNING xmax = 0 AS inserted;

    Ships today. 202 with a job id, then the client polls. The upsert is what makes a re-scan idempotent, and `xmax = 0` is how the job separates new invoices from ones it had already filed.

    The only control on this screen that writes anything.

  6. 6Share

    POST /api/shares {invoice_ids?, owner_name?, account_id?}

    shares · newinvoices

    -- only when the caller sent no ids: snapshot the whole view
SELECT id FROM invoices ORDER BY issued_on DESC NULLS LAST, id;

-- who this goes out as, resolved before the insert:
-- GET {unipile_dsn}/api/v1/accounts -> the mailbox and its name
-- name = account.name or the local part of the address

INSERT INTO shares
  (token, owner_key_hash, invoice_ids,
   owner_name, owner_email, created_at, expires_at)
VALUES ($1, $2, $3::jsonb, $4, $5, now(), now() + interval '7 days');

    The only write the flow makes, and the only place the owner's identity is decided. `invoice_ids` is a JSONB snapshot and is never updated: a later scan must not widen a link that has already been sent. The two owner fields are frozen for the same reason - disconnecting a mailbox must not change what an already-sent link says about who sent it. Returns {token, url, owner_key, owner_name, expires_at}, and the owner key is returned exactly once - only its sha256 is stored.

    The click is the share - there is no dialog to open first, so this button is the request. See 02-link.html for what comes back.
